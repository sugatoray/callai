# GAP_CONTEXT.md — Why Each Gap Exists

The *why* behind every entry in `GAP_ANALYSIS.md`: deliberate scope cut, genuine oversight, or technical blocker. Add or remove an entry here in lockstep with `GAP_ANALYSIS.md` — one gap, one reason.

- **hermes limits**: deliberate (fail closed) / harness limit. `-t` takes toolset names only and no toolset is read-only (`file` includes write_file and patch). `--continue` is refused (CA-15a): `hermes chat --continue` only resolves the latest `cli` (or `tui`) session (hermes_cli/main.py `_resolve_last_session`), so with callai's `--source tool` it would continue the user's interactive chat instead of callai's last run. `--resume ID` works. (`--system-prompt` was refused too until CA-21 let adapters set env vars; it now goes in `HERMES_EPHEMERAL_SYSTEM_PROMPT`.) Usage/cost exist only in `hermes -z --usage-file`, and `-z` approves every tool call, so it can't be the base mode.
- **pi `@` prompts refused**: deliberate (fail closed). pi reads any message starting with `@` as a file, even after `--`, and has no escape. Changing the prompt (e.g. adding a leading space) would break byte-exact delivery, so the user decides.
- **grok limits**: `/` prompts refused deliberately (fail closed): grok runs known slash commands (e.g. `/compact`) even with leading spaces, `--verbatim` or `--prompt-json`, and has no escape. No `--sandbox` in the mapping, deliberately (CA-11): every profile (`workspace`, `read-only`, `strict`) still allows writes inside the working directory, so it adds nothing to `read-only` (no write/shell tools offered); for `auto` it would confine writes to the working directory, but it needs bubblewrap on Linux and grok refuses to start without it, so adding it would break `auto` on machines without bwrap. Owner decided (after CA-11): keep it opt-in (`-- --sandbox workspace` or `GROK_SANDBOX=workspace`), documented as a CAUTION in the README and a caveat in DESIGN §7.
- **claude-code bypass as root**: harness limit. claude refuses `--dangerously-skip-permissions` / `bypassPermissions` as root unless `IS_SANDBOX=1`; callai doesn't set it, because that would sidestep a safety check on the user's behalf.
- **opencode refusals**: deliberate (fail closed, DESIGN §7). Its `plan` agent denies edits but allows shell, so it isn't read-only. `--auto` approves everything, so there's no edits-only level. `run` has no system-prompt option. Revisit if opencode adds them (or via a generated agent config).
- **Windows idle-stdin**: deliberate cut in CA-19. The 3s wait uses `select`, which only works on sockets on Windows; a reader thread would be needed, and an abandoned thread blocked on `sys.stdin` can crash interpreter shutdown. Revisit if anyone runs callai on Windows from an agent.
- **Stub-model fixtures**: blocker. Model APIs (OpenAI, xAI, Hugging Face router) are denied by the environment's network policy and there are no API keys/HF_TOKEN. Fixtures come from real harnesses talking to `conformance/tools/stub_llm_server.py`; re-record against real models when access exists.
- **stream-json coverage**: shipped in CA-14 with one recorded tool-call stream per harness (stub model) plus grok's refusal and unknown-model streams. Other codex item types (file_change, mcp_tool_call, web_search) and other harnesses' failed-tool events follow the same schema but weren't recorded: scripting them needs more stub tool calls, not a design change.
- **Live smoke tests for five harnesses unverified**: blocker, same as the stub-model fixtures: no API keys and model APIs denied by the network policy. The tests exist and skip; run `CALLAI_LIVE=all uv run pytest -m live` where access exists.
- **Fan-out shared working directory**: deliberate scope cut (CA-15c). Isolating each harness (temporary git worktrees) changes what the harness edits and needs cleanup rules; documented instead ("prefer `,` for tasks that edit files"). `-v` lines aren't prefixed because the runner copies stderr byte-exact; prefixing would need a per-harness tee.
- **superagent grok-cli unsupported**: deliberate. Both CLIs install `grok` with different flags; the owner chose xAI's official CLI (DESIGN §11). Could be added as a separate `grok-superagent` tool if asked.
